# 07 — Risks and Open Questions

## Risk register

| Risk | Why it matters | Mitigation |
|---|---|---|
| **API surface ambiguity** (`http/API` vs. `ApiNew` vs. `ApiNew2` vs. `api2`) | Migrating a dead variant wastes effort; missing the live one silently breaks mobile clients. | Do not begin Phase 5 without Phase 0's live-traffic audit (access logs/APM/mobile telemetry, not code inspection alone). |
| **Plaintext secrets in `http/Application.cfc`** | Live production exposure today (SendGrid, payment gateway/GZPay, API basic-auth creds). | Rotate in Phase 0, independent of migration timeline. Audit whether any creds are embedded in a mobile app binary — that's a cross-team/app-release dependency, not purely backend. |
| **Status logic drift across 8-10 call sites** | The single biggest correctness risk during transition: two systems could disagree on a parcel's status simultaneously if customer-facing tracking and admin cut over on different dates. | Cut over customer tracking and bema-admin parcel status in the **same deployment window** (see [06-phased-rollout-plan.md](06-phased-rollout-plan.md)); run the explicit status-distribution reconciliation from [05-data-migration-strategy.md](05-data-migration-strategy.md) before trusting the new column. |
| **Payment gateway continuity** | 7 gateways (PayPal, AuthorizeNet, CyberSource, PayFlowPro, Sage, InternetSecure, GZPay) currently live. | Each needs its own sandbox-verified Node port and rollback plan; cut over one gateway at a time, keep legacy checkout path toggle-able per gateway until proven. |
| **Shipping integrations (UPS/FedEx/USPS)** | Not fully enumerated in this audit — call sites (`com/portline/shipping/`) need confirmation of whether they're synchronous in checkout or async/cron-driven. | Follow-up code search required in Phase 0 before Phase 3 checkout work is scoped in detail. |
| **Undocumented `config` single-row table** | Cross-cutting coupling: shipping/estimate dates used across many modules. | Migrate early (Phase 1) as a typed settings table, not late, since later phases will implicitly depend on its values. |
| **Unbounded CSV export (9,999 rows, synchronous)** | Latent DoS/performance risk today; must not be ported as-is. | Mandatory redesign as an async job in Phase 4 (see [03-target-architecture.md](03-target-architecture.md) §5). |
| **Coupons scope boundary** | Risk of Phase 1's schema accidentally omitting a column another in-scope module depends on (e.g. checkout/invoicing referencing coupon codes/discounts inline). | Verify no shared tables/columns between coupons and parcels/orders in Phase 0 before finalizing the exclusion boundary. |
| **Large historical dataset** | Naive single-shot extraction would degrade the live production MSSQL database and is impractical at this data volume. | Batched, resumable, idempotent ETL as specified in [05-data-migration-strategy.md](05-data-migration-strategy.md) §2. |
| **Password hash migration** | Existing CF password hashes likely can't be verified by a new hashing library without knowing the exact legacy algorithm/salt scheme. | Confirm exact current hashing implementation (`user.hashPassword(pw, salt)`) in Phase 0/1; decide between a re-hash-on-next-login strategy or a one-time migration script. |

## Open questions (require client/stakeholder decision)

1. **Status priority-order discrepancy**: the bema parcels list query checks hold flags before `delivered`; the single-parcel `read()` function checks `delivered` before hold flags (see [02-parcels-domain-analysis.md](02-parcels-domain-analysis.md) §2.3). Which order reflects the intended business rule? This must be resolved before Phase 1's status-computation function is finalized, since it affects how historical and future parcels are classified.
2. **External/mobile API migrate-vs-rewrite decision**: the client has indicated they'll confirm separately whether the external API (`http/API`/`ApiNew`/`ApiNew2`/`api2`) needs to be migrated at all. Phase 0 produces the audit; the actual decision is pending client input (see [06-phased-rollout-plan.md](06-phased-rollout-plan.md) Phase 5).
3. **Content-editing ownership for static pages**: bema's `content/` module currently allows editing some public-facing content. Once public pages move to SSG (Phase 2), does content editing move to the Phase 4 admin rebuild, stay bridged to the legacy bema content module temporarily, or move to a different mechanism (e.g. a headless CMS, or git-managed content)? Needs a decision before Phase 2 is finalized.
4. **Coupons module long-term fate**: confirmed out of migration scope, but is it expected to remain permanently on the legacy CF stack (implying legacy infrastructure can't be fully decommissioned in Phase 7), be deprecated/removed from the business, or be migrated later as a separate, unscoped project? Affects Phase 7's "full legacy decommission" exit criteria.
